DyHub 的 star 数跳到 30 了。

说实话，30 这个数字没什么好吹的，放在 GitHub 上排不上号。但这是我从九月七号推第一行代码开始，整整两个月、断断续续的业余时间换来的。10 个 fork，0 个 open issue——说明确实有人 clone 下来跑过，而且没跑到提 issue 那一步就用了。

这就够了。一个做抖音弹幕采集的小众工具，能被 30 个人点一下 star，我觉得值。

## DyHub 是干什么的

一句话：一个抖音直播弹幕的采集和分发中台。

我自己要接弹幕做东西的时候，最烦的就是抖音的私有协议。今天能用的 protobuf 解码，明天抖音改个字段号就全废了。而且弹幕、礼物、进场这些事件散落在不同的 wss 帧里，消费端得自己去跟原始协议较劲。

DyHub 的思路是把所有脏活累活收在采集层，外面只暴露一种标准化的事件。抖音那边改协议，我改翻译层就行，接弹幕墙、做弹幕游戏、喂 AI 的消费端一行都不用动。

这是我写第一个 commit 就定下的规矩，也是整个项目最值钱的部分——不是某个花哨功能，是这个解耦。

## 两个月踩的坑，比 star 值钱

这两个月我大半时间不是在加功能，是在填坑。有些坑现在还在脑子里。

**第一个坑：礼物事件凭空消失。** 最开始连上直播间，弹幕、进场、点赞都正常，唯独礼物没有。查了半天才发现，抖音 webcast 服务端对游客连接不推礼物事件，只推给带 `sessionid_ss` 登录态的连接。得手动从浏览器 F12 复制一整行 Cookie 贴进控制台。这个体验极其原始——这也直接促成了后面要讲的扫码登录。

**第二个坑：多房间礼物互相抢。** 同账号同一时间只能在一个直播间，多个房间共用一个 Cookie，礼物信息就互相竞争，经常只有一个房间能收到。后来加了"每房间独立 Cookie"，让每个房间用自己的登录态，才算解决。这个改动在 commit 里标着 PR #5。

**第三个坑：protobuf 字段号错位。** 有一次礼物和进场的字段全读成 0，因为 User 和 GiftStruct 的字段编号跟抖音实际下发的对不上。修这个花了我一整天，最后对着抓包数据一个个字段号核对。

还有 Docker 里 Chromium 默认共享内存只有 64MB 会崩，得加 `--shm-size=2g`；抖音的 `createTime` 时而秒时而毫秒，得统一成毫秒；同一次连击礼物会推多条消息，得按 `giftId + groupId` 合并去重。

这些坑没有一个写在文档里，全是跑起来才撞上的。这大概就是开源的真相——别人 star 你，是因为你替他把坑填平了。

## 双内核，是我做的最重要的技术取舍

项目里有个环境变量 `DYHUB_COLLECTOR`，两个值：`browser` 和 `lightweight`。

浏览器内核是默认的。跑一个真实 Chrome，打开直播间页面，用 CDP 旁观 wss 帧。好处是稳——页面自己跟着抖音协议走，我不用管签名；坏处是重，一个房间吃小两百兆内存，冷启动要 3 到 15 秒。

轻量内核是纯代码直连 wss，自己搞签名、心跳、ack。连接秒级，一个房间二十兆。但纯 HTTP 逆向，在容器或数据中心 IP 下容易被风控拦。

两个内核产出的是同一种事件，消费端完全无感。我一开始只写了浏览器内核，后来被朋友催着加了轻量的——他机器上没 Chrome，跑不起来。

这个取舍我纠结过。两套内核意味着两套维护成本。但直播采集这个场景，有人要长期稳定挂生产，有人就验证一下跑完即走，需求差太远，一套内核没法通吃。最后决定都留。

## 接下来，我打算做两件事

Star 涨得慢，方向不能停。接下来的两个版本，我把精力放在这两件事上。

### 一、控制台集成抖音扫码登录

前面说了，现在拿登录态得手动 F12 复制 Cookie。这个流程太反人类——打开开发者工具、切 Network、刷新、找请求、复制整行 Cookie，新手十有八九卡在这步。礼物事件拿不到，还以为是 bug。

下一步我要把扫码登录做进控制台：控制台里弹一个二维码，手机抖音 App 扫一下，确认登录，`sessionid_ss` 就自动存进服务端了。整个流程不用再碰开发者工具，也不用把 Cookie 复制来复制去——说实话 Cookie 这种凭据在剪贴板里留着，本身就不太安全。

技术上，二维码登录是抖音 Web 端现成的能力，浏览器内核里本来就开着 Chrome，直接复用它的登录页就行。难点不在扫码本身，在拿到回调后怎么安全落盘、怎么跟现有的每房间独立 Cookie 机制衔接。

### 二、解析直播间用户的会员等级和勋章

这个其实是写这篇时翻源码才发现的一个"漏掉的数据"。

抖音的 User protobuf 里本来就有 `level` 字段（字段号 6），代表用户等级。但看我现在的归一化代码，`toUser` 只取了 id、昵称、头像、secUid——`level` 被我直接丢弃了。数据已经到了手里，我没接。

勋章也是同理。直播间里用户的勋章、粉丝团灯牌这些身份标识，目前都没解析。

下一步要做的：把 `level` 接出来，补上勋章和灯牌的解析（这块要在 proto 里加字段，得重新对着抓包核对），然后在控制台的弹幕流里，用户昵称旁边直接显示等级和勋章图标。

这个功能对做数据看板、做观众画像的人有用——你想筛"等级 40 以上、带某枚勋章的发言"，现在只能看到昵称，加了等级和勋章就能过滤了。

## 写在最后

30 个 star 不会让我一夜成名，DyHub 也成不了那种几千 star 的明星项目。它就是个解决具体问题的工具，有人需要，有人用，这就够了。

我越来越觉得，做开源这件事，最值得高兴的不是 star 数，是某个凌晨收到一条 issue，说"这工具帮我省了两天的活"。

那个比 30 个 star 实在多了。
