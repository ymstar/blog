我们团队有个内部工具叫 TeamAgent。说"内部工具"其实不太准确——它是一整套让多个 AI Agent 协作完成研发任务的系统，跑了大半年，现在是我们做需求的常规路径。

一句话说清楚它干什么：你给它一个 GitLab Issue，它自己拉一支队伍——需求工程师、设计工程师、编码工程师、代码审查员、验证员——把需求拆开、分配、做掉、提交 MR。中间不需要你插手，除非有关键决策要你拍板。

这篇文章不讲怎么用它——它是个内部工具，不会开源。我想讲的是这套东西背后的工程取舍：多 Agent 协作这个被外界讨论得很虚的话题，我们到底怎么落地的，撞了哪些墙。

## 先说清楚：这不是"多个 Agent 一起聊天"

很多人对"多 Agent 协作"的想象是——几个 Agent 在一个群里你一言我一语，互相 ping，最后涌现出一个结果。我们最早也这么想过，试了，放弃了。

原因是 Agent 之间没有可靠的共享状态。A 说"我做完了用户接口"，B 根本不知道 A 说的是哪个接口、做没做完、能不能用。靠对话维持状态，等于靠传闻维持一个项目的进度——信息会丢、会歪、会过期。

所以我们做的第一件事，是让"任务板"成为唯一的共享状态。

任务板就是一个 JSON 文件，存在 `.ipd/{issue_iid}/team/tasks.json` 里。每个任务有五个关键字段：`content`（一句话说清做什么）、`blocked_by`（依赖哪些任务先完成）、`target_files`（要碰哪些文件）、`status`（pending / in_progress / completed）、`owner`（谁在做）。

TeamLeader 把需求拆成任务写进这个文件，角色 Agent 从这个文件认领任务，做完再写回去。所有协作都围绕这个文件发生，Agent 之间不需要互相打招呼。

![任务在 Agent 间的流转](/img/post-img/teamagent-task-handoff.png)

这张图是任务从发布到完成的全过程。几个细节值得单独说一下。

**认领用原子锁。** 两个 Agent 同时认领同一个任务会打架。我们用 `acquireWriteLock()` 包了一个读-检查-写的临界区，认领时先锁住、检查 owner 是不是空的、写自己的 id、释放锁。代码就几行，但解决了一个真实的并发问题。

**blocked_by 保证顺序。** 任务 C 依赖任务 A 和 B，那 C 的 `blocked_by` 就是 `["1", "2"]`。认领 C 的时候系统会检查 A 和 B 是不是都 completed 了，没完成就拒绝认领。这样 TeamLeader 拆任务的时候只要把依赖关系标对，执行顺序就是自动的——不用人为调度谁先谁后。

**完成即解锁。** 一个任务被标记 completed 后，系统会扫一遍所有 pending 任务，把那些 `blocked_by` 已经全部满足的挑出来，告诉 TeamLeader"这几个可以开始了"。这个通知是写在 `finish_task` 的返回里的，不需要额外的轮询。

## 编排：场景是个阶段依赖图

任务板解决了"谁做什么"的问题，但没解决"按什么顺序做"。

一个全栈需求，总不能编码工程师先冲上去写代码，然后才发现设计文档还没出。顺序很重要，而且不同类型的活顺序不一样——bug 修复是"复现→调试→验证"，页面搭建是"设计→Schema→审查→验证"，不能套同一个流程。

我们的做法是把每种工作流抽象成一个"场景"，每个场景就是一张阶段依赖图。

```
全栈场景的依赖图：
Spec → Design ∥ Page Design → Task Planning → Backend Dev ∥ Frontend Dev → Test → Review → Verify
```

这是个 DAG。Design 和 Page Design 都只依赖 Spec，可以并行跑；Backend Dev 和 Frontend Dev 各自依赖前序，也能并行；Test 要等前后端都完成。每个阶段声明它产出什么文件（artifacts）、依赖哪些阶段、由哪个角色负责。

TeamLeader 启动一个需求时，先选场景，然后把场景的阶段图读进来，按依赖关系驱动执行。一个阶段的所有任务完成了，标记这个阶段 done，下一批依赖满足的阶段就可以启动。

这套机制最值钱的地方在于——阶段图是数据，不是写死的流程。每个场景的 `phases` 字段是个数组，TeamLeader 拿到的是结构化数据，恢复中断、生成执行计划、校验产出物都靠它。我们后面做会话恢复的时候，这张图救了命。

## 角色：25 个纯常量对象

讲完了任务和场景，该说"谁"了。

系统里有 25 个角色：编码工程师、调试工程师、代码审查员、结果验证员、页面搭建师、安全红队蓝队……每个角色就是一个 TypeScript 常量对象，长这样：

```typescript
export const TEAM_LEADER_ROLE: Role = {
  name: 'team-leader',
  prompt: 'You are the team leader...',
  allowedTools: [],
  deniedTools: ['Write', 'Edit', 'teamagent_commit_dev', ...],
};
```

关键设计：角色的 prompt 不是一段写死的文本，而是运行时用 `composeRolePrompt()` 拼出来的。拼接顺序是固定的：

1. **team-mate 基座**——所有角色共享的协作规则（怎么认领任务、怎么报告完成、工具失败怎么处理）
2. **GitLab 身份**——这个角色在 GitLab 里的权限边界（哪些操作不能自己干，得找 leader）
3. **角色专属 prompt**——这个角色具体做什么
4. **工具权限**——允许用哪些工具，禁止用哪些
5. **必需技能**——强制加载哪些 Skill

为什么要拆开拼，而不是一个角色写一整段 prompt？因为我们踩过一个坑。

一开始我们把所有规则都塞进角色 prompt 里。结果编码工程师的 prompt 里出现了"设计文档要上传到 Wiki"这种它根本不该管的事。角色之间开始互相耦合——改一条文档上传规则，得同时改编码工程师、设计工程师、代码审查员三个 prompt，因为这条规则被复制了三份。

后来我们立了一条规矩，写在团队的 CLAUDE.md 里当黄金法则：**这属于这里吗？会增加耦合吗？能复用吗？能说得更简单吗？** 每加一条规则都过这四问。属于所有角色共享的，进 team-mate 基座；属于特定流程的，进 Skill；属于角色核心职责的，才进角色 prompt。

这是个费力但值得的取舍。现在加一个新角色，只需要写它独有的那部分，基座和共享规则自动拼上来。我们靠这个把 25 个角色的 prompt 总量控制在了可维护的范围。

## 会话恢复：本地全丢了也能从 GitLab 重建

多 Agent 系统有个绕不开的问题——会断。

Agent 跑到一半，IDE 崩了、网络断了、上下文超长被压缩了，都常见。一个全栈需求跑下来要 spawn 七八个 subagent，中间任何一个断掉，整个流程就卡住。如果断点恢复做不好，这套东西就是个玩具——能跑 demo，不能跑生产。

我们花在会话恢复上的精力，不比花在编排机制上的少。

![会话恢复断点推断](/img/post-img/teamagent-resume-inference.png)

核心是一套叫 `determineResumePoint` 的算法。它要回答一个问题：**会话断了之后，从哪个阶段继续？**

回答这个问题比想象中难。你不能只看"上次跑到哪个阶段"——那个状态可能也丢了。我们用了三级回退：

**第一级，看显式记录。** 会话正常运行时，每个阶段完成会调 `complete_phase`，把已完成的阶段写进 `completedPhases` 数组。这是最可靠的数据源——要的就是它。

**第二级，看 GitLab 快照。** 如果本地 session 文件丢了（比如 worktree 被清掉了），但 GitLab Issue 上有任务看板的快照——我们每次任务状态变化都会 debounce 写一条 note 到 Issue 上——就能从快照里把任务列表和已完成阶段捞回来。

**第三级，看产出物。** 如果连快照都没有，就看磁盘上有没有这个阶段该产出的文件。Spec 阶段该有 `spec.md`，Design 阶段该有 `design.md`。文件在，就认为这阶段做过了。

三级都不灵的情况极少。只要 GitLab 还在，会话就能重建。

重建的时候还有个坑：**in_progress 的任务怎么办？** 一个任务被某个 Agent 认领、标记成 in_progress，然后那个 Agent 死了。这个任务既不能算完成，也不能被别人认领——因为 owner 字段还写着那个死掉的 Agent。

我们的处理是：恢复时把所有 in_progress 的任务重置回 pending，owner 清空。同时给那个死掉的 Agent 记一条"中断工时"，按它认领到中断的时间算，截断在 4 小时——超过的部分大概率是休眠，不算数。这条工时标记成 `aborted`，跟正常完成的工时分开放。

这一套做完，会话恢复才真正可用。不是"理论上能恢复"，是"本地文件全删了，从 GitLab 也能接着跑"。这点对我们敢把它用进真实需求很关键。

## 隔离：每个需求一个 worktree

最后说一个工程细节，但很重要。

多个需求并行跑的时候，如果都在同一个工作区里改代码，会互相踩。需求 A 在写 `user.ts`，需求 B 也在写 `user.ts`，git status 一团乱。

我们用 git worktree 做隔离。每个 Issue 启动时，`setup_worktree` 会在 `.claude/worktrees/issues-{iid}` 下拉一个独立的工作区，切到 `issues/{iid}` 分支。每个 worktree 里写一份 `.claude/settings.local.json`，配好这个工作区的工具权限和 MCP 服务器。subagent 在自己的 worktree 里干活，互不打扰。

worktree 创建的时候还会顺手做几件事：如果 Issue 绑定了 Iteration（迭代），就自动创建 MR 并把目标分支设成迭代分支；如果是 Hotfix 标签，目标分支设成 master。分支策略和 MR 创建都包在 `setup_worktree` 里，TeamLeader 不用单独操心。

有了这套隔离机制，三四个需求可以同时并行跑——每个一支队伍，各自一个工作区，各自一个分支，各自一个 MR。这是 TeamAgent 能进日常使用的物理基础。

## 它整个长什么样

把上面这些拼起来，整个系统是四层：

![TeamAgent 四层架构](/img/post-img/teamagent-arch-four-layer.png)

最上面是 Prompt 层——25 个角色和 16 个场景，运行时用组合引擎拼成完整的 role prompt。中间是工具层，11 个 MCP 工具模块，git 操作、任务管理、文档同步、会话恢复都在这里。底下是存储层，`.ipd/` 文件系统，session、tasks、specs 都落在本地，同时和 GitLab 双向同步。最底是平台层——GitLab 是真相之源，Dify 提供知识库，Claude MCP 协议负责工具通信。

四层之间的依赖是单向的：Prompt 层驱动工具层，工具层操作存储层，存储层对接平台层。没有反向依赖——工具层不会去改角色定义，存储层不会去调工具。这个边界守住了，系统的复杂度才没失控。

## 写在最后

做多 Agent 协作这件事，最大的误区是把它想得太浪漫。

它不是"一群智能体涌现出集体智慧"。它是工程——状态管理、并发控制、错误恢复、权限隔离，每一件都是枯燥的工程问题，每一件都得实打实地解决。Agent 之间的协作不会自己发生，得你设计一套机制让它在指定的轨道上发生。

我们这套东西跑了大半年，能稳定支撑日常需求，靠的不是某个聪明的 prompt，是任务板的原子锁、会话恢复的三级回退、worktree 的物理隔离、角色 prompt 的解耦——这些一件一件做出来的工程细节。

AI 写代码的能力在变强，但"让多个 AI 一起把一件事做完"这件事，需要的不是更强的模型，是更扎实的编排工程。这是我们做了大半年 TeamAgent 之后，最确定的一个判断。
